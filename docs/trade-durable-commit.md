# 成交保存与通知顺序

2026-09-11，SYS-11-07 / SYS-16-04。底层受控提交已接入，网页双窗口未开放。

## 变更

保留固定Crystal双方确认、相邻朝向、物品和金币容量预检查。预检查通过后由PlayerTradeCommit处理交换：暂存双方包裹/托管数组、堆叠Count、金币和托管金额，暂缓GainedItem/GainedGold包；使用原GainItem/GainGold算法交换。调用SaveTradeAccountsOrThrow，在等待旧异步保存完成后同步生成完整账户快照、写临时文件并Flush(true)、替换正式Server.MirADB。该方法校验参与者在当前玩家和账户集合内；保存错误向提交层抛出，不沿用会吞异常的SaveAccounts。

保存失败：恢复双方数组、物品堆叠数量、余额和负重，丢弃到账消息，双方解锁但保留交易窗口/托管；提示保存失败，需要重新双确认。

保存成功：结束双方交易，记录转移，再发送暂存到账消息和成功确认。通知失败只记录错误，不回滚已保存归属；另一方仍可收到成功消息。物品定义元数据可能提前发送，但不代表所有权变更。没有新增玩法或改变掉率。

## 已验证

CrystalContentTests整套通过（本地.runtime/trade-durable-tests.log）：

- 用目录占据临时存档路径制造真实文件写入失败。堆叠3+1在内存合并后回滚为原3/1，双方金币及托管恢复；没有GainedItem/GainedGold/TradeConfirm泄漏。
- 保存失败后只有一方确认不能成交；重新双确认只交换一次。
- 成功落盘后模拟一方确认通知抛错，不回滚所有权，也不阻断另一方确认。
- 独立写入子进程真实调用TradeConfirm；到账/成功通知发生时正式账户文件已存在。成功后直接强制结束进程，新读取进程读取成交时保存的正式Server.MirADB，而非另存的验证副本，双方980/1020金币、两件唯一物品、+3/+5属性与持久321正确。
- 原满包预留、双方满包互换、取消、存档快照与既有商店/掉落/技能回归保持通过。
