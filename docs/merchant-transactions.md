# 比奇收购与修理流程

2026-09-08。本轮先补服务流程和事务保护，**不认证当前报价为官服1.76数值**。

## 取证与范围

固定候选 [mrzhqiang/mirserver-1.76@39e17246](https://github.com/mrzhqiang/mirserver-1.76/tree/39e17246a32247a2c43c4cc481e97e88c692fa53/Mir200/Envir) 的MerChant.txt第26/50/54行定义了比奇城屠夫(313,271)、新人村屠夫(649,591)、边界村屠夫(293,603)。肉店.txt提供收购入口；戒指店/手镯店/项链店.txt都列出购买、出售、修理、特修及类别限制。已保存来源哈希到server/content/merchants.json。

原客户端FState.pas的DSellDlg：Prguse392，窗口(328,163)，物品区域(27,67)，确认393在(85,150)。直接使用已有原图，背包点选物品放入业务格；不提前从背包移除。原NPC11增加12帧（3方向×4），继续按固定WIL/WIX导出。

只开启已存在的肉类收购与11件首饰对应类别的出售/修理。没有把向导扩成万能商人，没有导入脚本里未经校对的干肉和扩展商品。

## 服务器事务

桥接请求通过有上限的WorldRequests队列交给Crystal单游戏线程，避免从网络线程读取/修改可变角色库存。

选择背包物品 → 服务器校验商人/距离/会话页面/类别/存活/持久/余额 → 使用真实UserItem.Price或RepairPrice报价 → 单次令牌确认 → 游戏线程重新检查物品ID、数量、属性、持久、费用和NPC上下文 → 调用原SellItem/RepairItem。

报价不直接扣款；确认时状态改变则拒绝并要求重报。令牌提交前消费，不能重复执行。出售在删除整件/整组物品前先检查金币上限，补足上游整组出售分支的缺口。取消连接的排队操作不会执行；已经处理的操作通过原SellItem、ItemRepaired、GainedGold/LoseGold回包更新浏览器。客户端迟到报价不能覆盖后来选中的物品或重新打开已关闭窗口。

当前出售一次为业务格中的整件/整组；拆分和数量选择继续由HUD-04跟进。完整跨断线事务恢复仍在NET-01中，不因已有取消保护就标为全完成。

## 价格与持久：哪些已知，哪些冲突

运行逻辑来自固定 [Crystal PlayerObject](https://github.com/Suprcode/Crystal/blob/0e315fe327192afe52c3d7357ddd1f5b7e26c5b8/Server/MirObjects/PlayerObject.cs) 与Shared/Data/ItemData.cs：

- 出售收入为当前Price()/2（整数）。
- 普修使用RepairPrice×NPC倍率；特修再乘3。
- 普修减少 `(最大持久-当前持久)/30` 的持久上限，再修满；特修保持上限；原单件附加属性保留。

旧 [Delphi ObjNpc.pas](https://github.com/pangliang/MirServer-Delphi/blob/f829679d24acb3a097d396d737ab067db2c88ca2/EM2Engine/ObjNpc.pas) 的GetUserItemPrice/GetSellItemPrice/ClientQueryRepairCost/ClientRepairItem存在区别：肉有独立品质价格分支，收购用ROUND；修理价格按当前物品价、缺失持久比例和配置计算。其特修查询与扣款的舍入顺序也不同。该源码同样是候选，不能直接当作唯一官服实现。

例如基础价200、MaxDura10000、CurrentDura7756且无附加的肉：Crystal收入94；旧Delphi肉价分支和四舍五入约为89（未计其他候选商人价配置）。两者不一致。因此任务表保留精确报价校准；当前版本展示的是运行服务器返回的真实费用，不在前端手写一个自称“1.76”的数字。
